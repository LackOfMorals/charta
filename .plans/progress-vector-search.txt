DECISIONS (from the numbers)
  * Hand-written SIMD assembly (NEON/AVX2): NOT worth it now. The scan is memory-bandwidth bound at
    scale (1M x 384 float32 = 1.5 GB in 7 ms is about 220 GB/s on this machine) and the pure-Go kernel
    already runs at about 6 G multiply-adds per second per core. Assembly would mean two kernels, CPU
    detection and upkeep for a small gain. Revisit only if a profile on target hardware shows the kernel,
    not memory, as the limit.
  * int8/float16 quantisation: not needed below a few million vectors; the memory cap
    (WithMaxVectorCacheBytes) is the pressure valve. Revisit if users hit it.
  * Approximate index (pure-Go HNSW): not now. 1M vectors search in 7 ms here and perhaps 20-40 ms on a
    4-core laptop. A proposal would be justified past roughly 5M vectors, or when a latency budget under
    10 ms on small machines is required. The Matrix/Hit API would not change: an HNSW graph would
    replace Matrix.Search behind the same procedure.
  * The cost that did matter was the COLD BUILD (30 us per vector). Done (8x faster, 3.7 us per vector):
      - measured first: fetching a row is 3.6-4.4 us; SQLite json_extract costs 11-17 us a row because it
        parses the whole document, so pushing extraction into SQL does not help;
      - fetch the raw props text and skip to the vector property in Go (vector.StoredVector), no Node, map
        or boxed []any; parse the numbers with a fast parser (up to 19 digits, within 4e-16 of strconv,
        which is plenty for float32; a stored embedding has 17 digits and strconv costs 45 ns a number
        against about 8 ns here); a first version only fast-pathed 15 digits and gained nothing on real
        data, which the benchmark with 17-digit numbers caught;
      - hand the rows to a pool of up to 8 parser goroutines (the parse is 10 us, the fetch 4), so the build
        runs at the fetch speed; builders are merged and normalised in parallel at the end.
    The remaining floor is the fetch of the ~4 KB props text per node. A binary side table
    charta_vectors(index_id, node_id, blob) would cut the row to ~1.5 KB but needs writes to keep it in step
    (and the bulk importer bypasses the interpreter), so it is not worth it at 0.4 s per 100,000.
    Also tried: mmap_size on the read pool (211 -> 197 ms at 10k, within noise), not adopted.

KNOWN LIMITS (documented in README/AGENTS.md)
  * node vector indexes only; relationship indexes are validated but not searchable.
  * a write by another process to the same file is not seen until reopen.
  * a search sees committed data newer than its snapshot (the matrix is "latest committed"); hit nodes that
    its own snapshot cannot see are skipped, so a result can contain fewer than k rows in a race.
