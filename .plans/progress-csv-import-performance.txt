CSV import performance (examples/csvImport) — measured 2026-10-09, Apple M5 Max, file database
Data: import.csv, 3,145,832 API request log rows, 598 MB.
Model: (:Client)-[:MADE]->(:Request)-[:TARGETS]->(:Instance), (:Request)-[:USING]->(:UserAgent)
  = 3,176,261 nodes, 9,437,496 relationships; converted to 631 MiB of node/relationship CSV (convert: 2.0 s).

Import (DB.Import, FormatCSVNodes / FormatCSVEdges, one transaction per file):
  request nodes: 500k per file, ~22.3 s each (~45 us/node, 3.3 MiB/s)
  relationships: 1.5M per file, ~11.8 s each (~7.7 us/edge, 2.3 MiB/s)
  total 3 min 36 s = 58k nodes+relationships/s; peak heap during import 331 MiB; database file 1,686 MiB.
  Constraints found: importer reads a whole file into memory (ReadAll) and accepts at most 500 MiB per reader,
  so the data had to be split into files; a failure rolls back only the current file.
  Hotspot to investigate: node insert is ~6x slower than edge insert (node_labels trigger with recursive CTE,
  JSON props, checkImport?).

Queries on the full graph (3.1M requests), first run, no extra indexes:
  count requests by status               6.8 s
  busiest clients (aggregate over MADE) 22.0 s
  requests per user agent               29.6 s
  one client's requests (by ip)          3.5 s
  requests to one instance by status    27.8 s   (2,038 rows: scans every Request instead of starting at the Instance)
  clients reaching the same instances   20.5 s
  errors (status>=500) per region       21.1 s
  whole-run peak RSS 15.3 GB (the interpreter caches every node/relationship it touches; no eviction).
Findings: (1) node import speed, (2) MATCH starts at the leftmost node, not the selective one,
  (3) aggregations over millions of nodes cost ~7 us/node and hold everything in memory (RSS).

Change 1 (cypher/interp/reverse.go): a plain chain pattern whose last node is a better start than its first
  (bound variable > property equality > label > nothing) is walked from the last node with directions flipped.
  Skipped for path variables, groups, WHERE/prop references to pattern variables, var-length rels with a variable.
  TestReversedPatternsAgree compares with forwards on random graphs (55 of 65 runs used it).
  3.1M-request graph, "requests to one instance, by status": 27.8 s -> 2.1 s. Other queries unchanged (they aggregate everything).

Change 2 (node insert): profiling showed bulk node insert spent ~85% of its time in the node_labels triggers
  (even a trigger that inserted one row cost 7 us/row; the recursive-CTE triggers cost more even when their WHEN was
  false). Labels are now written in Go (store.InsertNode, interpreter createNode/persistLabels), triggers dropped.
  Not helpful (measured): PRAGMA temp_store=MEMORY, larger cache_size, prepared INSERT statements.
  BenchmarkImportCSVNodes 100k rows: 36k -> 101k rows/s. Full import: 3m36s -> 2m17s (92k nodes+rels/s).
  Relationship import ~137k rows/s (1.5M-edge file: 11.8 s earlier run, 15.6 s in the second; likely noise/db size).

Change 3 (streaming CSV import): importCSVNodes/Edges read and insert row by row (no ReadAll, no 500 MiB cap; the old
  LimitReader silently TRUNCATED a larger CSV without an error). ValidateImported returns immediately when the database has
  no constraint or vector index (it used to re-read every imported row to find that out).
  BenchmarkImportCSVNodes 101k -> 122k rows/s, ...Edges 137k -> 168k rows/s.
  Full 3.1M-request import: 2m17s -> 1m56s (108k nodes+rels/s); peak heap during import 334 MiB -> 31 MiB.
